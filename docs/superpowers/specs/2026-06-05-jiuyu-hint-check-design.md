# 九屿提示与检查分级设计

## 背景

九屿当前已经完成微信小游戏单场景数独主循环，包含棋盘渲染、选格、填数、笔记、擦除、撤销，以及本地存档与继续游戏。

接下来的优先项是“提示与检查”。这一阶段不能只补两个按钮，而是要把“帮助强度”设计成和题目难度一致的体验能力。当前产品基线已经明确两条原则：

- 提示要有教学感，而不是直接变成答案按钮
- 不同难度的辅助强度要不同，不能让新手和专家看到完全一样的帮助

因此，本设计的目标不是做一个统一强度的提示系统，而是做一套直接绑定 `puzzle.difficulty` 的分级提示与检查能力。

## 目标

- 为当前小游戏主场景增加 `提示` 与 `检查` 两个可用工具按钮
- 将提示层级与检查强度直接绑定到 `puzzle.difficulty`
- 让主场景 UI 气质随题目难度分级变化
- 保持提示先帮助思考，再逐级变具体
- 保持高难度下的帮助更克制，不直接暴露答案信息
- 保持现有棋盘输入、笔记、撤销、存档主流程不被破坏

## 本次范围

### 包含

- 新增难度策略表，按题目难度控制提示与检查行为
- 新增纯逻辑检查模块
- 新增纯逻辑提示模块
- 工具栏增加 `提示`、`检查` 两个入口
- 在主场景增加轻量反馈文案与目标格/错误格高亮
- 在不改变核心布局的前提下，按难度切换 UI 视觉气质
- 为不同难度返回不同层级的提示结果
- 为不同难度返回不同强度的检查结果
- 补充对应纯逻辑测试与工具栏命中测试

### 不包含

- 一键填入答案
- 自动实时排错
- 高阶技巧，如 `box-line reduction`、`x-wing`
- 设置页里独立配置辅助强度
- 复杂提示面板、弹窗、教程系统
- 统计页里的提示次数/错误次数展示完善

## 绑定规则

本阶段直接采用方案 A：提示与检查强度绑定 `puzzle.difficulty`。

首版按以下 4 档定义统一策略：

- `beginner`
- `intermediate`
- `skilled`
- `expert`

当前题库中虽然实际只有 `beginner`，但结构上先把四档策略定义完整，后续题库扩展时不需要重做提示与检查架构。

## 方案对比

### 方案 A：主场景硬编码分支

在 `js/main.js` 中直接按题目难度写 `if/else`，分别处理提示和检查。

优点：

- 起步快

代价：

- 很快会把主场景逻辑变得拥挤
- 难以测试
- 后续扩技巧、扩题库、扩提示层级时维护成本高

### 方案 B：难度策略表

将“难度 -> 检查方式 / 提示上限 / 文案风格”抽成独立配置，主场景只消费结果。

优点：

- 边界清晰
- 易测
- 易扩展

代价：

- 首轮需要多一层策略模块

### 方案 C：难度策略表 + 提示逐级升级

在方案 B 基础上，再让同一局里连续点击提示时按层级逐步升级，但每个难度有自己的上限。

优点：

- 最符合“教学感”
- 最符合按难度分级的产品基线
- 后续可平滑扩展更多技巧

代价：

- 比纯策略表多一点提示状态管理

## 最终方案

采用方案 C：难度策略表 + 提示逐级升级。

核心思路是：

- `检查` 负责控制反馈强弱
- `提示` 负责控制帮助深浅
- 题目难度越高，越少直接暴露答案信息
- 主场景不直接判断复杂逻辑，而是调用独立的策略、检查和提示模块

## 难度策略

### `beginner`

- 检查：允许较强检查，手动检查时执行答案检查
- 提示：允许逐级到 `answer`
- 文案：解释更完整，偏陪练
- 视觉：更可爱、更轻松，颜色更柔和，反馈更有陪伴感

### `intermediate`

- 检查：手动检查，仍可执行答案检查，但反馈语气更克制
- 提示：最多到 `technique`
- 文案：给方向和简短解释
- 视觉：延续轻松和亲和感，但比 `beginner` 更收敛

### `skilled`

- 检查：只做冲突检查，不判断当前填写是否等于最终答案
- 提示：最多到 `technique`，但更偏方向与技巧，不直接给格子答案
- 文案：简短、专业
- 视觉：专业、简洁、干练，弱化装饰感

### `expert`

- 检查：只做最克制的手动冲突检查
- 提示：只给 `technique`
- 文案：最短、最专业
- 视觉：最克制、最清爽、最数据化

## 视觉分级策略

提示与检查不只影响逻辑反馈，也影响当前小游戏主场景的视觉气质。这里采用“同一套结构，不同难度切换视觉语言”的原则：

- 棋盘结构、按钮位置、交互路径保持一致
- 变化的是颜色、字重、反馈样式和文案语气
- 不把四档难度做成四套完全不同的页面，避免破坏熟悉感

### `beginner` / `intermediate`

整体方向：

- 画风更可爱
- 气质更轻松
- 更有陪伴感

视觉特征：

- 颜色更柔和，允许更温暖或更明亮的辅助色
- 工具栏与反馈区边角和块面感更柔软
- 提示与检查反馈文案更像陪练，而不是系统警告
- 错误提示避免强攻击性红色，优先用柔和提醒

### `skilled` / `expert`

整体方向：

- 专业
- 简洁
- 干练

视觉特征：

- 颜色更克制，减少跳跃装饰色
- 字重、留白和分隔更偏工具化与专业化
- 反馈区更短、更清楚，避免过多鼓励式修饰
- 提示与检查表现更像解题辅助，而不是陪练对话

### 当前阶段的实现边界

本阶段允许随难度切换的视觉项：

- 棋盘背景与高亮色
- 工具栏按钮底色、文字色、激活态风格
- 反馈区颜色、字重和语气
- 错误标记与提示目标格的表现强度

本阶段不做：

- 不同难度切换不同布局
- 不同难度切换不同按钮位置
- 独立主题配置页
- 复杂插画、动效系统、皮肤系统

## 检查系统设计

### 两类底层能力

#### 冲突检查

检查同行、同列、同宫是否出现重复填写。

特点：

- 不依赖完整答案
- 帮助较温和
- 更适合高难度保留解题感

#### 答案检查

检查当前已填写值是否与题目 `solution` 一致。

特点：

- 反馈更强
- 更直接暴露正确性
- 更适合低难度和新手帮助

### 难度到检查方式的映射

- `beginner` -> `solution`
- `intermediate` -> `solution`
- `skilled` -> `conflict`
- `expert` -> `conflict`

## 提示系统设计

### 提示层级

- `direction`
- `cell`
- `technique`
- `answer`

含义如下：

- `direction`：告诉用户先看哪一宫、哪一行或哪一列
- `cell`：指出一个可突破的格子
- `technique`：说明这里依赖的技巧
- `answer`：给出格子和值

### 难度到提示上限的映射

- `beginner` -> `direction -> cell -> technique -> answer`
- `intermediate` -> `direction -> cell -> technique`
- `skilled` -> `direction -> technique`
- `expert` -> `technique`

### 首版技巧范围

首版仅做以下三类能力：

- `naked-single`
- `hidden-single`
- `basic-elimination`

其中：

- `naked-single`：某格候选数只剩一个
- `hidden-single`：某行、列或宫中，某数字只剩一个可落位置
- `basic-elimination`：可生成方向型提示的基础排除结论

当前阶段不做更高阶技巧，避免在棋盘主循环刚稳定后过早扩复杂度。

## 结果对象设计

### 提示结果

提示模块统一返回：

```js
{
  level: "direction",
  technique: "naked-single",
  message: "先看左上这一宫，数字 7 只剩一个合适的位置。",
  targetIndex: 19,
  value: "7"
}
```

字段含义：

- `level`：提示层级
- `technique`：涉及的技巧名；纯方向提示可为 `null`
- `message`：给用户显示的文案
- `targetIndex`：如果已定位到格子，则带出格子下标
- `value`：仅答案层提示需要带出建议值

### 检查结果

检查模块统一返回：

```js
{
  mode: "conflict",
  hasIssue: true,
  message: "当前有 2 个填写与答案不一致。",
  issueIndexes: [19, 27]
}
```

字段含义：

- `mode`：本次使用的检查模式
- `hasIssue`：是否发现问题
- `message`：可直接显示给用户的反馈文案
- `issueIndexes`：需要在棋盘中轻量标记的格子下标

## UI 与交互入口

### 工具栏

工具栏从当前 3 个按钮扩为 5 个：

- `笔记`
- `撤销`
- `擦除`
- `提示`
- `检查`

### 反馈方式

当前小游戏仍采用单场景 Canvas 结构，因此本阶段不引入复杂弹层和教学面板，而是先采用轻量反馈：

- 在主场景增加一块状态反馈区
- 显示提示文案或检查结果
- 棋盘上增加目标格高亮或错误格标记
- 反馈区与标记样式允许随难度切换视觉气质

这样做的原因是：

- 当前结构中最重要的是保持输入路径顺滑
- 高频辅助操作不应频繁打断用户
- 后续若要升级为更完整提示面板，仍可复用底层结果结构

## 模块拆分

### `js/services/difficulty-policy.js`

职责：

- 定义难度到策略的映射
- 提供每个难度对应的 `checkMode`、`hintLevels`、`copyStyle`

### `js/services/checker.js`

职责：

- 负责纯检查逻辑
- 提供冲突检查、答案检查和按难度执行检查的统一入口

导出：

- `checkConflicts(game)`
- `checkAgainstSolution(game)`
- `runDifficultyCheck(game, difficulty)`

### `js/services/hint-engine.js`

职责：

- 负责纯提示逻辑
- 根据当前难度和当前提示进度返回下一条提示

导出：

- `getNextHint(game, difficulty, hintState)`

### `js/main.js`

继续作为主场景状态持有者，只负责：

- 接收按钮事件
- 调用检查与提示服务
- 根据当前难度选择对应视觉配置
- 存储轻量反馈状态
- 触发重绘

### `js/ui/toolbar.js`

职责扩展为：

- 绘制 `提示`、`检查` 两个新增按钮
- 返回对应命中结果

### `js/scene/board-scene.js`

职责扩展为：

- 支持绘制错误格标记
- 支持绘制提示目标格高亮
- 支持按视觉配置切换棋盘与辅助状态样式

### `js/ui/theme-policy.js`

职责：

- 定义难度到视觉风格的映射
- 为 `beginner / intermediate` 提供更可爱的主题
- 为 `skilled / expert` 提供更专业简洁的主题
- 统一输出主场景需要的颜色、按钮态与反馈样式配置

## 状态流

`main.js` 新增以下轻量状态：

```js
let feedbackMessage = "";
let feedbackType = "info";
let issueIndexes = [];
let hintState = {
  currentLevel: null,
  targetIndex: -1
};
```

同时，主场景按当前 `difficulty` 读取对应主题配置，但主题本身不进入可编辑业务状态。

### 点击提示

流程：

1. 读取当前题目 `difficulty`
2. 调用 `getNextHint(game, difficulty, hintState)`
3. 更新 `feedbackMessage`
4. 更新 `hintState`
5. 若返回 `targetIndex`，则同步高亮对应格子

说明：

- 首版即使返回 `answer`，也只做提示，不自动填入

### 点击检查

流程：

1. 读取当前题目 `difficulty`
2. 调用 `runDifficultyCheck(game, difficulty)`
3. 更新 `feedbackMessage`
4. 更新 `issueIndexes`
5. 若无问题，则给轻量正反馈

### 继续编辑

用户执行填数、擦除、撤销等操作后：

- 清空旧 `issueIndexes`
- 重置旧的提示目标
- 必要时清空上一次反馈文案

避免旧提示或旧错误标记持续误导用户。

## 存档策略

当前阶段仍仅持久化：

- `game`
- `selectedIndex`
- `noteMode`

本阶段不把以下状态写入 `currentGame`：

- `feedbackMessage`
- `feedbackType`
- `issueIndexes`
- `hintState`

原因：

- 这些都属于瞬时辅助状态
- 恢复继续游戏时没有必要恢复提示上下文
- 可以控制存档结构继续保持轻量

## 验收标准

- 不同题目难度下，提示层级符合难度策略
- 不同题目难度下，检查强度符合难度策略
- `beginner` 可以最终获得答案提示
- `expert` 不直接获得答案提示
- `skilled` 与 `expert` 不执行答案检查
- `beginner / intermediate` 与 `skilled / expert` 在 UI 气质上有明确差异
- `提示` 与 `检查` 不破坏现有填数、笔记、撤销、本地存档闭环

## 验证方案

### 自动化验证

- 继续运行 `node --test tests/game-engine.test.js`
- 为 `difficulty-policy`、`checker`、`hint-engine` 补纯逻辑测试
- 为工具栏按钮扩展补命中测试

首版关键自动化用例：

- `beginner` 执行答案检查
- `skilled` / `expert` 只执行冲突检查
- `beginner` 提示允许升级到 `answer`
- `intermediate` 提示最多到 `technique`
- `expert` 不返回答案层提示
- 提示和检查结果对象结构稳定
- 新增 `提示` / `检查` 后工具栏命中区域仍正确
- 不同难度主题下工具栏可读性和反馈对比度保持可用

### 手工验证

在微信开发者工具小游戏模式中检查：

1. 不同难度题目点击 `提示` 时，返回层级符合预期
2. 不同难度题目点击 `检查` 时，反馈强弱符合预期
3. 提示目标格高亮能正确显示与清除
4. 检查错误格标记能正确显示与清除
5. 提示与检查不会破坏现有存档恢复、笔记、撤销
6. `beginner / intermediate` 的页面气质更可爱亲和，`skilled / expert` 更专业简洁

## 风险与边界

- 当前题库实际只有 `beginner`，实现时需要先保证结构上支持四档，验证上先以 `beginner` 为主，再用测试数据覆盖其他档位
- 若提示服务直接依赖 UI 文案，将来扩语言或扩教学面板会变难，因此结果对象与文案生成职责要保持清晰
- 若视觉分级直接写死在绘制逻辑里，后续会和提示/检查逻辑耦合，因此主题配置需要独立
- 若过早做复杂弹窗，会把当前阶段拉成 UI 重构，应先坚持轻量反馈路线
- 若后续加入自动候选数清理，提示逻辑需重新评估候选数来源，但不构成当前阶段阻塞

## 结论

本阶段的正确实现方式不是“补一个 hint 按钮和一个 check 按钮”，而是围绕 `puzzle.difficulty` 建立一套分级辅助系统：

- 新手能得到更具体的帮助
- 熟练和专家用户保留更多解题感
- 提示先帮助思考，再逐级变具体
- UI 气质也随难度变化，但不打破同一套主场景结构
- 棋盘主循环保持稳定，不被复杂 UI 打断
