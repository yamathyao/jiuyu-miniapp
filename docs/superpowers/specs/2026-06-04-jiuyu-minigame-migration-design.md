# 九屿微信小游戏迁移设计

## 背景

当前仓库最初按微信小程序结构搭建，入口配置使用 `project.config.json + miniprogram/app.json`，并围绕 `pages`、`components`、`wxml`、`wxss` 组织视图层。现在项目目标明确切换为微信小游戏，因此需要将项目结构迁移到小游戏运行模型。

本次迁移不是简单把 `app.json` 改名为 `game.json`，而是把“页面驱动的小程序形态”调整为“单场景驱动的小游戏形态”。迁移的关键是保留已经成形的数独纯逻辑资产，同时重建入口、渲染层和输入分发方式。

## 目标

- 将项目入口迁移为微信小游戏结构
- 保留数独核心纯逻辑与测试护栏
- 用小游戏可用的渲染与触摸输入方式重建数独主场景
- 打通单场景数独最小可玩闭环

## 本次范围

### 包含

- 新建小游戏入口文件：`game.js`、`game.json`
- 新建小游戏运行目录与场景组织
- 迁移题库、数独工具函数、游戏引擎
- 使用 `Canvas 2D` 绘制棋盘、数字、候选数和底部操作区
- 实现选格、填数、笔记、擦除、撤销与高亮

### 不包含

- 首页
- 设置页
- 统计页
- 完成页
- 提示系统
- 检查功能
- 本地存档扩展
- 第三方游戏引擎接入

## 设计原则

1. 优先保留与运行形态无关的纯逻辑资产
2. 小程序页面和组件层不强保，避免无意义兼容
3. 先把数独主场景单独跑通，再考虑外围页面能力
4. 用最小可行渲染方案完成迁移，避免过早引入引擎复杂度

## 方案对比

### 方案 A：最小兼容迁移

- 保留数独纯逻辑
- 重建小游戏入口、主场景和输入系统
- 废弃小程序专属页面/组件视图层

优点：

- 能最大化复用已有数独规则逻辑
- 迁移边界清晰
- 风险主要集中在 UI 重建，而不是业务逻辑重写

代价：

- 视图层基本需要重做

### 方案 B：表面改名迁移

- 尝试把现有小程序入口与文件名改成小游戏形式
- 尽量保留 `pages/components/wxml/wxss`

优点：

- 短期看起来改动少

代价：

- 与小游戏运行模型不匹配
- 高概率在后续输入、渲染和结构上持续碰壁

### 方案 C：重建小游戏项目后再搬逻辑

- 从零创建标准小游戏骨架
- 再逐步迁入数独逻辑

优点：

- 项目结构最干净

代价：

- 短期需要同时理解两套目录语义
- 迁移期间上下文切换更多

## 最终方案

采用方案 A：最小兼容迁移。

核心思路是：保留 `game-engine`、`sudoku`、`puzzles` 和对应测试，把小程序专属的页面和组件视图层替换为小游戏单场景结构。项目将围绕“一个主数独场景 + 一个底部操作区”组织，而不是继续维持多页面路由模型。

## 保留资产

- `miniprogram/services/game-engine.js` 的规则逻辑思路
- `miniprogram/utils/sudoku.js` 的行列宫计算逻辑
- `miniprogram/data/puzzles.js` 的题库数据结构
- `tests/game-engine.test.js` 的逻辑测试护栏

这些模块都与页面系统弱耦合，适合迁移到小游戏目录后继续使用。

## 废弃范围

- `miniprogram/pages/*`
- `miniprogram/components/*`
- `miniprogram/app.js`
- `miniprogram/app.json`
- `miniprogram/app.wxss`
- 依赖 `wxml/wxss/page/component` 的视图组织方式

这里的废弃是结构废弃，而不是立刻删除所有文件。迁移过程中可以保留旧目录作为对照，等小游戏主场景跑通后再清理。

## 迁移后目标结构

```text
jiuyu-miniapp/
  game.js
  game.json
  project.config.json
  js/
    main.js
    constants.js
    data/

    utils/

    ui/
      toolbar.js
  tests/
    game-engine.test.js
```

## 模块设计

### `game.js`

小游戏入口文件，负责启动主逻辑。

### `game.json`

小游戏配置文件，用于替代小程序的 `app.json` 入口配置。

### `js/main.js`

职责：

- 初始化小游戏运行入口
- 获取画布上下文
- 初始化题局状态
- 统一分发触摸坐标到棋盘区或工具区
- 驱动重绘

### `js/scene/board-scene.js`

职责：

- 绘制数独棋盘
- 绘制 given、用户填数、候选数
- 绘制选中高亮、相关格高亮、相同数字高亮
- 计算棋盘点击位置对应的格子索引

### `js/ui/toolbar.js`

职责：

- 绘制底部数字输入区
- 绘制笔记、撤销、擦除按钮
- 计算底部操作区的命中结果

### `js/services/game-engine.js`

职责：

- 管理题局状态
- 提供填数、笔记、擦除、撤销等操作
- 输出高亮所需数据

### `js/utils/sudoku.js`

职责：

- 提供行、列、宫及相关格判断等纯函数

### `js/data/puzzles.js`

职责：

- 提供本地静态题库

## 渲染策略

首版迁移采用 `Canvas 2D`，不引入第三方游戏引擎。

原因：

- 当前核心场景只包含棋盘、数字、候选数和少量按钮区域
- `Canvas 2D` 足以支撑数独场景
- 减少引擎引入带来的目录、生命周期和调试复杂度
- 后续若要增强动效或增加复杂场景，再评估升级渲染方案

## 输入策略

所有输入统一按“触摸点坐标 -> 命中区域 -> 调用逻辑”处理：

- 点击棋盘区域：选中格子
- 点击底部数字区：输入 `1-9`
- 点击底部工具区：切换笔记模式、撤销、擦除

输入不再依赖小程序组件事件系统，而由 `main.js` 集中分发给 `board-scene.js` 和 `toolbar.js`。

## 第一批最小闭环

迁移后第一批只要求达到以下能力：

- 小游戏能成功启动
- 能看到静态数独棋盘
- 能点击格子
- 能输入数字
- 能切换笔记模式
- 能擦除
- 能撤销
- 能看到选中高亮、相关格高亮、相同数字高亮

这意味着外围页面和后续辅助能力都不纳入第一批迁移验收。

## 迁移顺序

1. 新建小游戏入口结构：`game.js`、`game.json`、`js/main.js`
2. 搬运纯逻辑层：`game-engine`、`sudoku`、`puzzles`
3. 让 `Canvas 2D` 先绘制静态棋盘和数字
4. 接通格子点击选中
5. 接通底部数字输入
6. 接通笔记、擦除、撤销
7. 补高亮和候选数绘制
8. 最后清理旧的小程序页面目录

将清理旧目录放在最后，是为了迁移过程中始终保留参考实现与回退线索。

## 验收标准

- 微信开发者工具能按小游戏项目打开
- 不再报“未找到 `game.json` 文件”
- 能进入单一数独场景
- 可以完成选格、输入、笔记、擦除、撤销
- `given` 格不可编辑
- 高亮逻辑与当前 `game-engine` 保持一致
- `tests/game-engine.test.js` 持续通过

## 验证方案

### 自动化验证

- 继续运行 `tests/game-engine.test.js`
- 确认逻辑迁移后行为与当前纯逻辑一致

### 手工验证

在微信开发者工具的小游戏模式中执行：

1. 打开项目，确认入口识别为小游戏
2. 确认不再报缺失 `game.json`
3. 进入主场景，确认棋盘正常绘制
4. 点击格子并确认高亮反馈
5. 输入数字并确认写入
6. 切换笔记模式并确认候选数显示
7. 执行擦除与撤销并确认状态回退

## 风险与边界

- 若试图强保小程序 `pages/components/wxml` 结构，会让迁移持续卡在运行模型不兼容上
- 若过早引入第三方游戏引擎，会放大当前迁移复杂度
- 若不保留逻辑测试护栏，UI 重建时容易把已有规则逻辑带坏

因此本次迁移应坚持“保逻辑、重建入口与场景、最后再清旧结构”的节奏。
