# 九屿本地存档与继续游戏设计

## 背景

小游戏主场景已经完成数独最小可玩闭环，当前支持棋盘渲染、选格、填数、笔记、擦除、撤销与高亮。用户已经可以正常完成一局的核心操作，但退出小游戏后会丢失当前进度，这会打断“随手打开、继续做题”的体验。

当前产品方向仍坚持“本地优先”，因此下一阶段最优先补齐的不是提示、统计或完成反馈，而是把“退出后还能继续上一局”这件事做稳。

## 目标

- 在微信小游戏中自动保存当前对局进度
- 再次启动时优先恢复最近一局
- 保留撤销历史，保证恢复后仍可继续撤销
- 保持当前单场景结构，不引入多页面或云端能力

## 本次范围

### 包含

- 新增小游戏本地存储封装
- 启动时尝试读取当前存档
- 无存档时按现有逻辑创建默认题局
- 在关键交互后自动保存当前状态
- 恢复 `game`、`selectedIndex`、`noteMode`
- 保留 `game.history`，让撤销能力在恢复后继续可用

### 不包含

- 多存档位
- 主动“新开一局”入口
- 按难度切题
- 存档列表或存档管理 UI
- 云同步
- 存档版本迁移系统

## 设计原则

1. 先保证“继续上一局”稳定可用，再考虑更复杂的存档管理
2. 存档能力只做薄封装，不把简单需求抽象成复杂状态系统
3. 优先复用现有 `game` 状态结构，避免额外映射层
4. 存档失败时不阻断游戏主流程

## 方案对比

### 方案 A：只保存题局状态

- 保存 `game`
- 启动时恢复棋盘内容
- `selectedIndex` 和 `noteMode` 重新置为默认值

优点：

- 实现最简单
- 状态结构最小

代价：

- 恢复后没有“继续做刚才那一步”的连贯感
- 用户需要重新选格、重新打开笔记模式

### 方案 B：保存题局状态与交互状态

- 保存 `game`
- 保存 `selectedIndex`
- 保存 `noteMode`

优点：

- 恢复体验更完整
- 仍然保持轻量

代价：

- 比方案 A 多一层交互状态恢复

### 方案 C：保存题局状态、交互状态与撤销历史

- 保存 `game`
- 保存 `selectedIndex`
- 保存 `noteMode`
- `game.history` 作为 `game` 一部分一并持久化

优点：

- 继续游戏体验最完整
- 恢复后撤销链不断
- 现有引擎结构天然支持，额外成本很低

代价：

- 存档数据比前两种方案稍大

## 最终方案

采用方案 C：自动本地存档 + 启动自动恢复 + 保留撤销历史。

实现上不新增复杂状态容器，而是在当前 `js/main.js` 的状态持有基础上增加一个存档读写层。启动时优先尝试读取最近一局，读取成功则直接恢复；否则按当前逻辑从本地题库初始化默认题局。后续每次发生关键交互后，都把最新状态写回本地存储。

## 模块设计

### `js/services/storage.js`

职责：

- 定义本阶段使用的存储 key
- 封装 `wx.getStorageSync`
- 封装 `wx.setStorageSync`
- 对读取失败或空值返回统一 fallback

该模块保持极薄，只服务当前“最近一局存档”场景，不提前扩展为通用存储平台。

### `js/main.js`

职责补充：

- 启动时加载最近一局存档
- 在无存档时创建默认题局
- 在用户完成关键交互后触发保存
- 在恢复后的首次绘制中直接反映焦点和笔记模式

`main.js` 仍然是当前场景的唯一状态持有者，避免把存档逻辑散落到棋盘或工具栏模块中。

## 存档数据模型

本阶段存档结构如下：

```js
{
  game: {
    puzzleId: "beginner-001",
    difficulty: "beginner",
    puzzle: "...",
    solution: "...",
    cells: [
      {
        index: 0,
        value: "",
        given: true,
        notes: []
      }
    ],
    elapsedSeconds: 0,
    mistakes: 0,
    hintsUsed: 0,
    history: [
      {
        index: 10,
        mode: "value",
        value: "",
        notes: []
      }
    ]
  },
  selectedIndex: 10,
  noteMode: false
}
```

说明：

- `game` 沿用现有引擎状态结构，不单独做转换
- `selectedIndex` 属于当前交互焦点，需要一并恢复
- `noteMode` 属于当前输入模式，需要一并恢复
- `history` 作为 `game` 的一部分保留，保证恢复后仍可撤销

## 存储键设计

当前阶段只使用一个 key：

```js
"jiuyu.currentGame"
```

原因：

- 当前只需要保存“最近一局”
- 单 key 读写简单、稳定、可预期
- 后续若扩展为多存档位，再单独设计索引结构

## 保存时机

以下操作完成后立即保存：

- 选中格子变化
- 笔记模式切换
- 普通填数
- 候选数切换
- 擦除
- 撤销

这样设计的原因是：

- 用户随时可能退出小游戏
- 当前状态量很小，频繁同步写入的成本可接受
- 比起延迟批量保存，立即保存更稳妥，也更容易验证

## 恢复流程

启动流程调整为：

1. 初始化 Canvas 与绘制依赖
2. 读取 `jiuyu.currentGame`
3. 若存档存在且结构可用，则恢复 `game`、`selectedIndex`、`noteMode`
4. 若存档不存在，则执行 `createGame(puzzles[0])`
5. 进入正常绘制与交互循环

本阶段不做“存档属于哪个版本”的判断，也不做题库兼容转换；若读取结果不完整，则直接回退到新建默认题局。

## 错误处理

- `wx` 不可用时，不启用存档能力，但不阻断当前启动逻辑
- 读取到空值时，按无存档处理
- 读取到结构异常值时，按无存档处理
- 写入失败时静默忽略，不打断当前交互

当前阶段不弹出错误提示，因为本地存档属于增强能力，不应破坏主玩法流畅性。

## 验收标准

- 首次启动无存档时，仍能正常进入默认题局
- 任意编辑操作后关闭小游戏，再次启动能恢复到最近状态
- 恢复后焦点格与笔记模式与退出前一致
- 恢复后可以继续执行撤销
- `tests/game-engine.test.js` 继续通过

## 验证方案

### 自动化验证

- 继续运行 `node --test tests/game-engine.test.js`
- 为存储相关纯函数或状态恢复分支补局部测试（若实现中拆出可测辅助函数）

### 手工验证

在微信开发者工具的小游戏模式中执行：

1. 启动项目，确认首次无存档时正常进入棋盘
2. 选中一个格子并输入数字
3. 切换笔记模式并操作候选数
4. 执行一次撤销
5. 关闭并重新打开项目
6. 确认棋盘内容、焦点格、笔记模式和撤销能力都已恢复

## 风险与边界

- 若未来引入计时器，`elapsedSeconds` 的恢复策略需要单独细化
- 若未来允许切换题目，单 key 模型需要升级为“当前局 + 存档索引”
- 若未来修改 `game` 数据结构，需要补存档兼容策略

在当前阶段，这些都不构成阻塞，应保持设计聚焦在“单局自动续玩”。
