# 九屿棋盘核心设计

## 背景

本设计用于落实九屿小程序第二阶段“棋盘核心”开发，并按本轮确认结果将笔记模式一并纳入当前迭代。目标是先把数独最核心、最高频的解题手感做稳，为后续的本地存档、提示系统、完成判断和统计打下可靠基础。

当前仓库已经具备页面、组件与服务层骨架，但棋盘页仍是静态占位状态。现阶段需要把“能稳定玩一局静态题目”的交互闭环打通，而不是扩展到排错、提示或存档。

## 目标

- 支持加载一局静态数独题目并渲染 9x9 棋盘
- 支持选格，并高亮当前格、同行、同列、同宫
- 支持在选中有值格子时高亮全盘相同数字
- 支持普通填数、擦除、撤销
- 支持笔记模式与候选数显示
- 保证题目给定数字不可编辑

## 本次范围

### 包含

- `pages/game` 页面状态编排
- `services/game-engine` 中的纯逻辑扩展
- `components/sudoku-board` 的动态渲染与点击事件
- `components/number-pad` 的输入事件透传
- `components/game-toolbar` 的笔记、撤销、擦除命令透传与状态反馈

### 不包含

- 冲突检查
- 正误判断
- 自动清理候选数
- 完成态判断
- 本地存档联动
- 提示系统接入

## 设计原则

1. 页面只负责状态编排，不直接操作单元格细节
2. 游戏规则与可编辑逻辑尽量沉到纯函数，便于后续补测试
3. 展示组件保持“输入输出清晰”，不承担业务状态源
4. 先保证交互路径稳定，再追求更多高级特性

## 方案对比

### 方案 A：页面控状态，逻辑下沉到引擎

- `pages/game` 持有 `game`、`selectedIndex`、`noteMode`
- `services/game-engine` 负责填数、记笔记、擦除、撤销、只读校验和高亮辅助数据
- 组件只接收展示数据并抛出事件

优点：

- 状态边界清楚
- 后续接存档、提示、完成判断时改动最顺
- 逻辑层天然适合做纯函数测试

代价：

- 页面需要承担少量状态路由职责

### 方案 B：组件内自管理状态

- 主要交互状态放进 `sudoku-board`
- 页面只做容器

优点：

- 页面表面代码更短

代价：

- 状态容易分散
- 后续接撤销、存档、提示时容易出现跨组件耦合

### 方案 C：全部状态集中到引擎

- 页面只转发命令
- 引擎返回完整状态树

优点：

- 业务逻辑非常集中

代价：

- 当前阶段会把简单页面交互过度抽象
- 开发速度与可读性都不占优

## 最终方案

采用方案 A：`页面控状态 + engine 管纯逻辑 + 组件只做展示/派发事件`。

这个方案最贴合当前项目骨架，也最适合作为后续阶段的演进基线。页面层负责承接微信小程序交互事件和 `setData`，引擎层负责维护数独局面的可编辑规则和操作结果，组件层只关心渲染与事件回传。

## 模块设计

### `pages/game`

职责：

- 初始化一局静态题目
- 维护页面级状态：`game`、`selectedIndex`、`noteMode`
- 把点击格子、输入数字、工具栏命令路由到引擎
- 把引擎结果转换为组件可消费的数据

页面不直接修改单元格内部结构，所有写操作统一通过 `game-engine` 完成。

### `services/game-engine`

职责：

- 创建游戏状态
- 校验格子是否可编辑
- 处理普通填数
- 处理笔记切换
- 处理擦除
- 处理撤销
- 根据选中格生成高亮辅助信息

这里尽量使用纯函数，输入旧状态和命令，输出新状态或展示辅助数据，方便后续用测试锁定行为。

### `components/sudoku-board`

职责：

- 渲染 81 个格子
- 显示 given / user / selected / related / same-value 等视觉状态
- 在无数字时显示候选数布局
- 点击格子时回传 `index`

该组件不保存业务真状态，只消费页面传入的数据。

### `components/number-pad`

职责：

- 渲染 1 到 9 的输入按钮
- 点击后回传数字值

当前阶段先不做复杂禁用态，只保留最基本的输入能力。

### `components/game-toolbar`

职责：

- 提供 `note`、`undo`、`erase` 命令入口
- 显示笔记模式当前是否激活

当前模板中的 `hint`、`check` 按钮可以暂时保留占位，但不纳入本次核心闭环。

## 状态模型

### 游戏状态

继续沿用 `createGame()` 的结果作为主业务状态：

```js
{
  puzzleId: "beginner-001",
  difficulty: "beginner",
  puzzle: "...",
  solution: "...",
  cells: [
    {
      index: 0,
      value: "",
      given: true,
      notes: []
    }
  ],
  elapsedSeconds: 0,
  mistakes: 0,
  hintsUsed: 0,
  history: []
}
```

### 页面状态

页面额外维护两个轻量交互状态：

```js
{
  selectedIndex: -1,
  noteMode: false
}
```

原因：

- `selectedIndex` 和 `noteMode` 属于当前交互态，不属于题局本身
- 把它们留在页面层，可以减少引擎对界面状态的感知

## 交互数据流

1. 页面加载时，从本地题库中取一题，调用 `createGame()` 初始化状态
2. 用户点击某个格子，页面更新 `selectedIndex`
3. 页面根据 `game + selectedIndex` 生成要传给棋盘组件的展示数据
4. 用户点击数字键：
   - 普通模式：对当前格写入数字
   - 笔记模式：对当前格切换该数字的候选标记
5. 用户点击擦除：
   - 普通模式：清空当前格 `value`
   - 笔记模式：清空当前格 `notes`
6. 用户点击撤销：回退最近一次可编辑操作

选格本身不进入历史栈，避免撤销时回退焦点而不是回退输入。

## 高亮规则

- 当前选中格高亮
- 与选中格同行、同列、同宫的格子高亮
- 如果选中格存在数字值，则全盘相同数字高亮
- `given` 格与用户填写格使用不同字重和背景色区分

高亮结果由引擎根据 `selectedIndex` 和当前棋盘状态计算，再交给棋盘组件渲染。

## 笔记模式规则

- 只有非 `given` 格可写入笔记
- 格子已有主值时，笔记模式下仍允许切换候选数，但普通填数时应以主值优先显示
- 重复点击同一候选数字时执行开关切换
- 候选数显示为格内 3x3 小数字布局

当前阶段不做自动清理候选数，保持行为简单且可预期。

## 撤销策略

撤销只覆盖用户可编辑操作：

- 普通填数
- 笔记切换
- 擦除主值
- 擦除笔记

撤销不覆盖：

- 选格
- 笔记模式开关

历史记录采用“必要字段快照”方案：每次编辑前记录目标格子的旧值、旧笔记和操作类型。当前阶段数据规模很小，这种方式最稳妥，后续也容易升级。

## 错误处理

- 未选中格时，输入、擦除、撤销都静默忽略
- 选中 `given` 格时，所有编辑操作静默忽略
- 撤销栈为空时，撤销静默忽略
- 重复切换同一笔记数字时，结果保持可预测的加减切换

当前阶段不弹错误提示、不做 toast，优先保持输入路径平滑。

## 验收标准

- 能加载静态题目并正确渲染 9x9 棋盘
- 能选中格子并显示同行、同列、同宫高亮
- 选中有值格子时，能高亮全盘相同数字
- 非 `given` 格可以输入数字
- 可以切换笔记模式并显示候选数
- 可以擦除输入值或笔记
- 可以撤销最近一步编辑操作
- `given` 格不可编辑，且视觉区分清楚

## 验证方案

### 逻辑验证

优先给 `game-engine` 补纯逻辑测试，覆盖：

- `given` 格不可编辑
- 普通填数写入正确
- 笔记数字切换正确
- 擦除主值和擦除笔记行为正确
- 撤销可恢复上一状态

### 页面验证

在微信开发者工具中进行一次手工 smoke test，覆盖：

- 点选不同格子时的高亮反馈
- 普通模式输入、擦除、撤销
- 笔记模式切换与候选数显示
- 点击 `given` 格时无法编辑

## 风险与边界

- 当前阶段若把 `hint`、`check` 一起实现，会稀释棋盘核心验证重点
- 若把过多界面状态塞进引擎，会让页面层与组件层边界变模糊
- 若不尽早把编辑逻辑沉到纯函数，后续接存档和提示时会出现重复逻辑

因此本阶段应坚持“小范围、强闭环”，先把数独最核心的输入和反馈体验做稳。
