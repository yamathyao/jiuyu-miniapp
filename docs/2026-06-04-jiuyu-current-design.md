## 当前结论

- 产品名称统一为 **方庭九屿**
- 产品核心仍是“日常可玩、专业可调”的单人本地数独体验
- 技术形态已从 **微信小程序** 切换为 **微信小游戏**
- 当前开发目标不再是多页面小程序，而是先完成 **小游戏单场景数独主循环**
- 所有用户可见文本统一走 i18n 层，品牌名 **方庭九屿** 保持不翻译

## 产品定位

方庭九屿不是偏工具化的冷数独，也不是重度闯关小游戏。它更像一个愿意让人每天打开、能安静做题、又保留一定专业控制感的数独产品。

当前保持不变的产品原则：

- 打开快，进入主玩法快
- 棋盘手感优先于外围页面装饰
- 本地优先，避免首版被账号、服务端和社交系统拖重
- 提示要有教学感，而不是直接变成“答案按钮”
- 新手得到帮助，熟练用户不过度被打扰

## 当前平台与结构判断

项目最初按微信小程序结构搭建，围绕：

- `miniprogram/app.json`
- `pages/*`
- `components/*`
- `wxml / wxss`

来组织界面与逻辑。

现在项目目标明确切换为微信小游戏，因此后续设计基线调整为：

- 入口使用 `game.js`、`game.json`
- 运行结构以单主场景为核心
- 渲染方式采用 `Canvas 2D`
- 输入方式采用触摸坐标命中，而不是页面组件事件系统

这意味着小程序阶段的页面/组件结构不再是未来主线，只保留其中可复用的逻辑资产。

## 保留资产

小游戏迁移后仍应保留并复用的资产：

- 数独题库数据结构
- 数独坐标与宫格工具函数
- `game-engine` 中的题局状态、填数、笔记、擦除、撤销、高亮逻辑
- 现有 `tests/game-engine.test.js` 逻辑测试

这些模块和“是小程序还是小游戏”弱耦合，属于项目的长期核心资产。

## 当前交互基线

数独主场景继续沿用此前已收敛的棋盘核心规则：

- 选中格高亮
- 同行、同列、同宫高亮
- 若选中格有值，则全盘相同数字高亮
- 普通输入会写入主值并清空该格笔记
- 笔记模式下，数字输入切换候选数
- 擦除会根据当前模式清空主值或候选数
- 撤销仅覆盖可编辑操作，不覆盖选格行为

## 当前技术路线

当前技术路线统一为：

- **平台**：微信小游戏
- **渲染**：Canvas 2D
- **逻辑层**：纯 JavaScript + CommonJS
- **测试**：Node 原生 test runner，优先保护纯逻辑模块

不在当前阶段引入第三方游戏引擎，原因是：

- 当前场景复杂度还低
- 首要目标是尽快跑通主循环
- 过早引擎化会增加目录、生命周期和调试负担

## 当前目标目录

```text
jiuyu-miniapp/
  game.js
  game.json
  js/
    main.js
    constants.js
    data/
      puzzles.js
    services/
      game-engine.js
    utils/
      sudoku.js
    scene/
      board-scene.js
    ui/
      toolbar.js
  tests/
    game-engine.test.js
```

说明：

- `js/main.js` 负责启动、状态持有、输入分发和重绘
- `scene/board-scene.js` 负责棋盘绘制和格子命中
- `ui/toolbar.js` 负责数字区和工具区绘制及命中
- 旧 `miniprogram/` 目录只作为迁移过渡参考，不再代表最终结构
